# Участие в разработке EVA

Этот документ описывает, как вносить вклад в проект: сообщать об ошибках, предлагать улучшения и отправлять пул-реквесты.

## Сообщить об ошибке

1. Убедитесь, что такой ошибки ещё нет в [Issues](https://github.com/spiritlion/EVA/issues).
2. Создайте Issue с шаблоном **Bug report** (`.github/ISSUE_TEMPLATE/bug_report.md`).
3. Заполните: компонент, версию, шаги воспроизведения, ожидаемое и фактическое поведение, логи.

## Предложить улучшение

1. Сначала создайте Issue с шаблоном **Feature request** — и обсудите идею.
2. Только после согласования реализации приступайте к коду.
3. Пул-реквест ссылается на обсуждённый Issue (см. ниже).

## Ветки

Ветки называют по схеме `<тип>/<компонент>-<краткое_описание>`:

- `feat/core-telemetry-endpoint`
- `fix/agent-registration-crash`
- `docs/contracts-versioning`
- `refactor/core-storage`

Основная ветка — `master`. От неё создаются рабочие ветки, в неё — пул-реквесты.

## Пул-реквесты

При отправке PR обязательно:

- Указать связанный Issue: `Closes #12` или `Fixes #34` в описании — GitHub закроет Issue после мержа.
- Пройти тесты и валидацию контрактов (см. чек-лист в шаблоне PR).
- Дождаться ревью хотя бы одного мейнтейнера.

### Формат сообщений коммитов

Использовать префиксы по Conventional Commits:

- `feat(core): ...`, `fix(agent): ...`, `docs(contracts): ...`, `refactor(core): ...`, `test(core): ...`, `build(core): ...`

Это облегчает чтение истории и генерацию changelog.

## Внимание: контракты (EVA-Contracts)

`EVA-Contracts` — единый «язык» обмена между Core и Agent и версионируются по **SemVer** независимо от остальных компонентов (см. `EVA-Contracts/VERSIONING.md`).

Правила:

- Изменение существующего контракта **breaking** требует новой MAJOR-версии и обновления `CONTRACTS.md`.
- Совместимое расширение — MINOR; документарное исправление — PATCH.
- Выпущенные версии контрактов **неизменяемы** — изменения требуют новой версии.
- Любые правки контрактов проходят валидацию:
  - `tools/validate_schemas.py`
  - `tools/validate_examples.py`
  - `tools/validate_refs.py`

Риск изменения контрактов — главный повод для остановки обсуждения до начала работы.

## Непрерывная интеграция

CI автоматически запускает тесты и валидацию контрактов на каждый PR (см. `.github/workflows/ci.yml`). ПР-ы, не прошедшие CI, не мёрджатся.
