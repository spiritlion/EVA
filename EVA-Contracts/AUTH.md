# EVA Authentication — v1

Описание того, как Agent предъявляет Core свою идентичность и как устроен оборот ключей.
Контракт данных: `schemas/v1/security/agent-credentials.schema.json`.

## 1. Идентичность агента

Каждый Agent имеет уникальный идентификатор `agent_id` (UUID), который он указывает:

- в запросе регистрации (`registration/request`);
- в учётных данных (`agent-credentials`);
- в соединении WebSocket (`connection.hello`).

`agent_id` — постоянная идентичность узла, независимая от `node_id`, который Core выдаёт при регистрации.

## 2. Схемы аутентификации («schema»)

Контракт поддерживает две схемы. Для первой связки достаточно первой.

### 2.1. `bearer_token` — предустановленный токен (P1)

Пригоден для старта и одноранговой сети.

- Core хранит токен агента (выдаётся как секрет).
- Agent предъявляет его при каждом запросе.

HTTP:

```
Authorization: Bearer evatk_v1_9f2c4b6d8a0e1c3d5f7a9b2c4d6e8f0a
```

WebSocket: токен передаётся в `connection.hello` в поле `credentials.bearer_token`.

### 2.2. `auth_request` — вызов/подтверждение живой записи (P2)

Используется как дополнительный фактор или для одноразовых операций.

- Agent отправляет `nonce` и `timestamp`.
- Core подписывает `nonce` и возвращает подпись, Agent проверяет её.
- Гарантирует свежесть запроса, но не заменяет секрет.

## 3. Сценарии использования

### 3.1. HTTP-запрос

Каждый управляющий HTTP-запрос несёт учётные данные:

```
Authorization: Bearer <token>
```

- Core проверяет `agent_id` и `token`.
- Недействительные токены возвращают `401` (`error.schema.json`, code `AUTH_INVALID`).
- Нет аутентификации на публичных эндпоинтах регистрации (`POST /registration-requests`, `GET /registration-requests/{id}`) — там узел ещё не имеет токена.

### 3.2. WebSocket-соединение

1. Agent устанавливает WSS-соединение.
2. Отправляет `connection.hello` с `credentials`.
3. Core проверяет credentials, отвечает `connection.accepted` или `connection.rejected` (`code`, `reason`).

## 4. Выдача и ротация ключей

### 4.1. Первичная выдача (bootstrap)

- На этапе регистрации токена ещё нет.
- В административном сценарии Core выдаёт токен после одобрения узла.
- Способ доставки начального секрета — вне протокола (вводится оператором на стороне Core и Agent).

### 4.2. Ротация (P2+)

- Смена токена инициируется Core либо по сроку, либо оператором.
- Механизм сообщения ротации определяется отдельной спецификацией (в `CONTRACTS.md` — раздел Security, выдача ключей — P2).

### 4.3. Отзыв (P2+)

- При отзыве Core перестаёт принимать старый токен.
- Механизм аннулирования — P2, вне текущего контракта.

## 5. Какие типы событий связаны

Реестр (6.8) определяет `admin.registration.approved` / `admin.registration.rejected`.
Выдача токена логически следует за `admin.registration.approved`.

## 6. Открытые вопросы

- Стоит ли `credentials` в `connection.hello` сделать обязательным уже сейчас (P1), или только опциональным до полной настройки выдачи ключей?
- Нужен ли вариант с временным (single-use) токеном до появления постоянной инфраструктуры ключей?
